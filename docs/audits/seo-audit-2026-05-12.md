# SEO audit 2026-05-12

Branch: seo-security-improvements (off strip-template-chrome-anchor)
Scope: public-facing pages and supporting code only. Portal admin out of scope.
Auditor: Claude Code (Opus 4.7, 1M context) sub-agent

## Summary
- Total findings: 41 (critical: 1, high: 11, medium: 16, low: 9, info: 4)
- Top themes:
  - No Article JSON-LD on blog posts; BreadcrumbList missing on blog detail and category pages
  - Article frontmatter has no author field; all article tags are empty arrays, so tag pages, related-posts logic, and category context collapse
  - Hidden persona variants ship at initial render but only one is announced, leaving multiple H1/H2 in DOM with the same semantic level
  - Homepage uses `ProfessionalService` schema only (no `Organization` or `WebSite`+`SearchAction`); about page Person schema lacks job-title-affirming fields
  - Portal noindex enforced only on `/portal/login` markup; middleware does not emit `X-Robots-Tag` for protected routes
  - Three service detail pages skip FAQ schema; only `web-management` has one
  - Blog post cover images lack width and height attributes; loading="eager" used regardless of viewport
  - Public-facing `naming-preview.astro` is unlisted in audit scope but indexable and lacks the audit dimensions; flagged for triage

### [SEO-001] Blog detail pages missing Article JSON-LD
**Severity**: high
**Dimension**: 3 (Structured data)
**Files**: `src/pages/blog/articles/[slug].astro`, `src/pages/blog/case-studies/[slug].astro`
**Observation**: Neither template emits `Article` JSON-LD. Frontmatter carries `title`, `description`, `publishDate`, optional `updated`, optional `cover`, and tags, all of which are required or recommended Article properties. Without the schema, Google cannot promote the entries to article rich results, breadcrumb chips, or `datePublished` carousels.
**Recommendation**: Add `<script type="application/ld+json">` blocks with `@type: "Article"` (or `BlogPosting`), populating `headline`, `description`, `datePublished`, `dateModified` when present, `image` set to the per-entry OG png, `mainEntityOfPage` set to the canonical URL, and `author` once an author field exists (see SEO-005). On the case-study template, optionally use `@type: "Article"` with `about` set to the sector and use `Article.about` rather than inventing a non-standard type.
**Effort**: small
**Verification**: View source on a deployed article and case study page; confirm valid JSON-LD with required fields parses in Google's Rich Results test.

### [SEO-011] Multiple H1 elements per page on persona-variant routes
**Severity**: medium
**Dimension**: 4 (Headings), 13 (Persona variants), 14 (Accessibility)
**Files**: `src/pages/services.astro:13-24`, `src/pages/contact.astro:14-22`
**Observation**: Both pages render three `<h1>` elements (one per `data-vibe` or `data-frame` variant) in the DOM. The non-default ones carry `style="display:none"` and `aria-hidden="true"`, which keeps assistive tech from announcing them, but search crawlers still parse three H1s. Astro best practice and accessibility heuristics expect one H1 per document. The inline comment in `services.astro:9-12` acknowledges this is intentional "for SEO weight on segment-targeted copy"; that bet may be wrong: Google deduplicates equivalent headings and may interpret three H1s with the same role as a quality signal.
**Recommendation**: Choose one. Either (a) keep the default H1 as the only H1 in the DOM and render alternates as visually identical H1-styled paragraphs (no heading semantics), or (b) keep three H1s but accept that linting tools will flag this and that Google may not weight all three. Recommended: option (a). The variant text still ships to the page and is swap-visible, but only one element carries `<h1>` semantics. Same logic applies to stacked H2 variants on `index.astro:66-68`; H2s can repeat, so this one is less urgent.
**Effort**: small
**Verification**: View-source on `/services` and `/contact` shows exactly one `<h1>` element.

### [SEO-012] Portal middleware does not emit X-Robots-Tag header
**Severity**: medium
**Dimension**: 10 (Crawl directives), 9 (Robots)
**Files**: `src/middleware.ts:10-51`
**Observation**: Only `/portal/login.astro` ships `<meta name="robots" content="noindex, nofollow">`. Other portal routes (`/portal/dashboard`, `/portal/admin/*`, etc.) require auth and will redirect, but a probing crawler that sees the 302 to `/portal/login` may still index intermediate URLs without an HTTP-level signal. The middleware sets several security headers but no robots header.
**Recommendation**: In `middleware.ts`, when `context.url.pathname.startsWith('/portal')`, also set `response.headers.set('X-Robots-Tag', 'noindex, nofollow')`. This belt-and-suspenders the meta tag, covers redirect responses that have no HTML body, and makes the directive auditable from curl.
**Effort**: trivial
**Verification**: `curl -I https://codyasmith.com/portal/dashboard` returns `X-Robots-Tag: noindex, nofollow`.

### [SEO-016] Google Fonts loaded with no font-display swap on CSS request
**Severity**: medium
**Dimension**: 11 (Performance)
**Files**: `src/layouts/Base.astro:52`
**Observation**: The Google Fonts CSS URL ends with `&display=swap`, which is correct for non-blocking text rendering on initial paint. However the stylesheet itself is render-blocking because it is not preloaded as a stylesheet. Visitors with cold caches will wait one extra RTT to fetch the CSS before any text paints.
**Recommendation**: Add `<link rel="preload" as="style" href="<fonts-css-url>">` plus a `media="print" onload="this.media='all'"` toggle on the stylesheet link, or move to self-hosted woff2 with `font-display: swap` in `@font-face`. Preconnect to `fonts.googleapis.com` is already present. Optionally preload one critical weight (Inter 400 or Instrument Serif 400) as `font/woff2` to remove FOIT.
**Effort**: small
**Verification**: Lighthouse "Eliminate render-blocking resources" stops flagging the fonts CSS; "Preload key requests" passes for at least one font file.

### [SEO-018] Cover images load eagerly with no dimensions; below-fold images not lazy
**Severity**: medium
**Dimension**: 5 (Image SEO), 11 (Performance), 12 (Mobile)
**Files**: `src/pages/blog/articles/[slug].astro:78-96`, `src/pages/blog/case-studies/[slug].astro:118-137`
**Observation**: Both detail templates render the cover image with `loading="eager"` and no `width` or `height` attributes. **Effort**: small
**Verification**: Lighthouse "Properly size images", "Image elements have explicit width and height", and "Avoid an excessive DOM" stop flagging the cover. CLS on detail pages drops below 0.05.
